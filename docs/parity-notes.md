An exception before the commit call triggers one rollback attempt, whose own failure is logged and never replaces the original classification. The 500 or 503 of a failed write carries `writeOutcome`, which says what is known about the data and never changes the status. It is `notWritten` when no DML was sent, the rollback completed without error, or the server reported the transaction aborted as deadlock victim (1205). DML counts as sent only once an `INSERT` or `UPDATE` is dispatched (`src/EpiInfo.Data/Records/SqlRecordRepository.cs`, `WriteScope.MarkDmlSent`), so a write that fails before its first one, such as in the locked read, the page-row read or the in-transaction permission read, is `notWritten`, and so is an update that dispatched none and then fails to commit. It is `unknown` when DML was sent and neither a commit nor a completed rollback can be confirmed: the commit call failed or did not return, or the rollback itself failed. It is `written` when the store reported the commit and a later step failed before the response started, such as serialising the response, or when releasing the committed transaction or its connection failed (`ReleaseCommittedAsync`). The handler takes the request's record first: `written` once the store reported a commit, `notWritten` once it reported a result that wrote nothing or while no store write call was issued, and otherwise the store exception's own outcome, else `unknown` (`src/EpiInfo.Api/Errors/WriteOutcomeFeature.cs`; `src/EpiInfo.Api/Errors/ApiExceptionHandler.cs`, `ResolveWriteOutcome`; `src/EpiInfo.Data/Sql/SqlErrorClassifier.cs`, `ResolveWriteOutcome`). The client resends nothing on its own (`web/src/state/useRecordEditor.ts`, `saveFailureBanner`, `deleteFailureBanner`, `retry` and `saveAgain`; `web/src/api/errors.ts`, `isSafeToResend`). ### Design reconciliations

- **C-15: Date fields.** A `date` field is `YYYY-MM-DD` on the wire and is stored at 00:00:00 in its `datetime` column. Legacy keeps the time of day (`Epi.Core/Data/Services/CollectedDataProvider.cs:1302-1315`). The time-bearing types, Date/Time and Time, are unsupported and not seeded.
- **C-17: Navigator coordinates.** The Record DTO's `position` and `count` stay intrinsic in every response: over the active set when `recStatus` is 1, over all rows when it is 0. The navigator's "[n] of N" follows the deleted toggle. N is `count` with the toggle's `includeDeleted`; n is the requested `at` position, or the `position` returned by `GET .../records/{globalRecordId}/position?includeDeleted=<toggle>`, and never comes from search. Legacy numbers the open record, whose `UniqueKey` is k, by `Select Count(*) From [<base table>] Where UniqueKey <= k` with no `RecStatus` filter, so its "[n] of N" counts deleted rows too (C-5). It adds a `FKEY` filter only for a related view, and neither seeded form is one (`Epi.Enter.CheckCodeEngine/RunTimeView.cs:673-694`; the query is at `:687`). The target keeps that formula but applies it over the selected set: the active set `RecStatus = 1` (C-16), or every row with `includeDeleted=true`. With the toggle on, n and N equal legacy's. - **C-19: Five additive extensions**, each optional or extra, so every specified shape still holds:

  - search `excludeGlobalRecordId`;

  - `GET .../records/{globalRecordId}/position`, returning `{position, count}` over the selected set without changing the Record DTO (see C-17 for the legacy `UniqueKey <= k` count it replaces). It reads only the base table, so a known record whose page row is missing is still placed and never disappears. A known record outside the selected set, such as a deleted record with the toggle off, returns `position: null` with the set's `count`. When the toggle is switched off while a deleted record is open, the navigator therefore opens `at/{min(n, count)}`. ## Search semantics

`POST .../records/search` follows legacy Find, because the request's tie-break makes legacy semantics win (C-4). The records-list `q` keeps the request's case-insensitive "contains", because it has no legacy counterpart.

### Legacy extraction

- **Dialog**: at most six fields can be selected (`Epi.Windows.Enter/Dialogs/FindRecordDialog.cs:293-317`), and each control's text is trimmed (`:355-374`). A value splits on exactly `" or "`, `" OR "`, `" Or "` or `" oR "`, dropping empty entries. A leading `<=`, `>=`, `<>`, `>` or `<` is read as the operator, `=` by default, and stripped from the value (`:708-770`). Criteria on different fields combine with AND, and the alternatives of one field with OR.
- **Query**: the base table is `INNER JOIN`ed only to the pages that hold a criterion field (`Epi.Core/Data/Services/CollectedDataProvider.cs:1940-1967`). A system-field criterion maps to an unbound page with no table name, and the join then fails (the `GlobalRecordId` and `RecStatus` rows below). Predicates are built per type, as in the table below, and `RecStatus > 0` is appended (`:2249`). The open record is removed after the query only when the caller passes a non-null `currentView` with the searched view's name. The standard Enter Find command passes none (`Epi.Windows.Enter/Forms/EnterMainForm.cs:406-409`; `Epi.Windows.Enter/Dialogs/FindRecordDialog.cs:67, 80-81, 676`), so a matching open record stays in its result. Only the linked-record viewer passes one (`Epi.Windows.Enter/Forms/LinkedRecordsViewer.cs:292, 336`), and the provider then removes that record (`Epi.Core/Data/Services/CollectedDataProvider.cs:2256-2264`).
- **Hydration**: the matching base rows are re-read and each page is joined in memory; a base row without a row on some page is dropped (`:2289-2298, 2357-2375`). The result is therefore the matching base rows that have a row on every page, in no stated order.

| Field kind | Legacy | Target |
|------------|--------|--------|
| `text`, `multiline`, `legalValues`, except Phone Number | Blank text is rejected by the dialog (`FindRecordDialog.cs:611-643`). The operator prefix is stripped and ignored; a value left empty by a bare prefix such as `>` becomes `IS NULL` (`CollectedDataProvider.cs:2186-2193`). ### Target choices

The one list of Find departures and retentions (C-4, C-18):

- **Kept**: the six-field limit, so a seventh criterion field is a 400 on `criteria`; trimming of each string value; the split and prefix rules; AND across fields and OR within one. A field named twice is a 400, since the dialog cannot select a field twice.
- **Result set**: one statement `INNER JOIN`s the base table to every page table and applies the criteria. For the legacy searches that reach hydration, the all-page join reproduces legacy's final, hydrated result (base rows with every page row), though not legacy's two-step query. A legacy search on a system field fails at its join first (the `GlobalRecordId` and `RecStatus` rows above).
- **Set filter**: `RecStatus = 1`, or every row with `includeDeleted=true`, replacing `RecStatus > 0` (C-16).
- **Open record**: excluded on the server through `excludeGlobalRecordId` (C-19), before `total` and the cap. The id is matched exactly as a lookup by id matches it, so a spelling that differs from the stored id only by trailing spaces excludes nothing. This is a behavioural difference from standard Enter Find, which keeps a matching open record in its result, not only a change of timing. Legacy removed the open record only on the linked-record path, after the query ("Query" above).
- **Order and cap**: results are ordered by `UniqueKey` and capped at 200; `total` counts all matches and `truncated` is `total > 200`. Each item's `position` is its `ROW_NUMBER()` over the selected set by `UniqueKey`, computed before the criteria filter, so it equals the navigation position. Legacy had no order and no cap.
- **Parameterisation**: every value is a parameter, so quotes stay in `LIKE` patterns where legacy removed them. Text-family values are bound as Unicode `nvarchar(max)`, so a criterion reaches the comparison with the characters entered. Legacy did not keep them for every comparison: it bound the multiline 255-character comparison as `DbType.AnsiString` (`CollectedDataProvider.cs:2212-2222`), which its SQL Server driver sends as `varchar` (`Epi.Data.SqlServer/SqlDatabase.cs:525-526`), and it inlined the `LIKE` pattern (`CollectedDataProvider.cs:2205`) and the Phone Number value (`:2130`) as literals without the `N` prefix. Each reached the comparison in the code page of the database collation, 1252 for `SQL_Latin1_General_CP1_CI_AS`, with a character outside it best-fit mapped or replaced by `?` (on this server `CONVERT(varchar(50), N'Łódź 漢')` gives `Lódz ?`). Such a criterion could miss a stored value holding the original characters, or match one holding the mapped text; the target matches the characters entered. Legacy's plain equality already bound `DbType.String` (`:2231`), so it is unchanged.
- **Departures in the table**: number criteria compared exactly against integer columns, where legacy compared the criterion's rounded double text; ISO dates bound as `datetime`; a blank Option rejected cleanly instead of the legacy null dereference; JSON booleans accepted for checkboxes beside `Yes`/`(+)` → 1 and `No`/`(-)` → 0, case-sensitive; the system fields `GlobalRecordId` and `RecStatus` searched as base-table criteria, where the legacy join on their unbound page fails before any result; Yes/No fields not searchable.

### Grid q

The records-list `q` is a case-insensitive "contains" over the grid columns. It converts each column to `nvarchar(max)` (style 23 for `datetime`) and compares under `Latin1_General_100_CI_AS` with `LIKE @q ESCAPE '\'`, with `%`, `_`, `[` and `\` escaped in `@q`, so it does not depend on the database collation. A blank `q` applies no filter. A `q` of any length is that literal contains, never a 400. When its escaped and `%`-wrapped pattern is longer than SQL Server's 4,000-unit `LIKE` limit, that is a `q` longer than 3,998 characters counting each `%`, `_`, `[` and `\` as two, the one list statement instead runs the long-pattern program ("Wildcard patterns", below) over the same converted column texts under the same collation. There `q` is one literal run between two `%`: its seek finds candidates with `PATINDEX` on prefixes of `q`, written with `%`, `_` and `[` as the one-member sets `[%]`, `[_]` and `[[]`, because `PATINDEX` takes no `ESCAPE` clause, and each candidate compares the whole `q` with `=`, which needs no escaping. So a long `q` lists the records the one `LIKE` that SQL Server refuses to run would list, where `Latin1_General_100_CI_AS` matches an expansion (`æ` and `ae`, `ß` and `ss`) or ignores a character (`NUL`, the soft hyphen) included: `GridQ_PastTheLikePatternLimit_KeepsTheCollationsExpansions` (`tests/EpiInfo.Api.Tests/Records/ListAndSearchTests.cs`) lists a record storing `æ` for a 4,001-character `q` holding `ae`, and the reverse, and `SearchStatementBoundsTests` compares the long and the native filter on seeded texts holding `fi` under filters carrying `ﬁ`, `NUL`, the soft hyphen and `😀`. The one bound left, that the seek looks for 33 prefixes of `q`, is recorded under "Parity gaps" ("Find wildcard patterns longer than 4,000 code units"). `q` has no legacy counterpart.

### SQL Server limits

Two SQL Server limits bear on a Find search: a command binds at most 2,100 parameters, of which `sp_executesql` takes two, and an `nvarchar` pattern of `LIKE`, `PATINDEX`, `CHARINDEX` or `REPLACE` holds at most 8,000 bytes, 4,000 UTF-16 code units, beyond which each fails with error 8152, while `=` has no such limit. Measured on the rehearsal SQL Server 2022, an `sp_executesql` call with 2,098 statement parameters runs and one with 2,099 fails with the 2,100-parameter error.

- **Alternatives**: a search holds any number of alternatives, as in legacy, bounded only by the 1,048,576-byte body. While it holds at most 2,000 alternatives other than `IS NULL` across its fields, the Find statement binds one parameter per such alternative, plus at most three (the selected-set `RecStatus`, the `TOP` cap and the excluded id), so at most 2,003 parameters. With more, every condition is bound packed: its `IS NULL` alternatives become one `IS NULL` term, and its other values, grouped by operator and by the type their scalar parameters bind (a number on an integer column binds `bigint` or `decimal`), one `nvarchar(max)` parameter each holding a packed list: ASCII text giving the element count and the cumulative offsets of the element tokens, ten digits each, followed by the tokens. It is matched by `EXISTS (SELECT 1 FROM (<the list decoded, one row per element>) AS [d] WHERE <the operator's predicate on [d].[v]>)`: cross-joined `VALUES` digit tables, as many as the count has digits, number the elements, and `SUBSTRING` reads each token at the offsets the list gives, so the count, the offsets and the values all stay in the parameter. The decoded set is ordered by value under `TOP (2147483647)`, which makes SQL Server decode each element once and lets it match the set with one merge or hash semi-join, or scan it from one spool for the other operators, rather than decode the list again for every row. A packed statement alone also ends with `OPTION (USE HINT ('DISABLE_OPTIMIZER_ROWGOAL', 'FORCE_LEGACY_CARDINALITY_ESTIMATION'))`: SQL Server costs the decoding as almost free, so under the row goal of `TOP`, which buys nothing because `COUNT_BIG(*) OVER ()` reads every match first, or under the cardinality estimator of level 130 and later, it can still plan it once per candidate row, and the hints make every level plan it once per list as levels 100 and 110 do without a row goal. Measured 2026-11-26 through the builder on `CaseReport`, one `GlobalRecordId` equality and 5,000 `LIKE` alternatives exceed the 30-second command timeout unhinted at levels 100 and 160, and at 160 with the row-goal hint alone, and run in 0.9 s with both; a `CaseReport1.Address` search of one equality and 5,000 patterns, which the row-goal hint alone takes from 5.6 s past the timeout at 160, runs in 3.7 s. A condition then binds at most twelve parameters, and one more when it holds patterns longer than 4,000 units, which are never packed ("Wildcard patterns"), so a six-field search stays far under the limit. Each element is built as the scalar parameter it replaces and decodes to exactly that parameter's SQL type and value: text through the hexadecimal of its UTF-16LE code units, read back as `nvarchar(max)`, or for a `LIKE` pattern as the `nvarchar(4000)` that `LIKE` converts its `nvarchar(max)` parameter to, which keeps every code unit and compares under the column's collation as a parameter does; integers, bits and dates as text read back into their own type; an integer column's `decimal` criterion as its text read back as `decimal(38, s)`, `s` the largest scale of its list; floats as the sign, exponent and fraction of their IEEE 754 bits at fixed widths, rebuilt by exact arithmetic, because SQL Server's text-to-float parse is not correctly rounded. Packed and per-alternative statements therefore return the same rows, which `SearchStatementBoundsTests` (`tests/EpiInfo.Data.Tests/Records/SqlRecordRepositoryTests.cs`) compares on both forms, also under non-default session `SET` options. The decoding uses no `OPENJSON`, `JSON_VALUE`, `STRING_SPLIT` or `xml` method, so it runs at every database compatibility level (Compatibility level, above). Final run, 2026-11-26, on the run tree, on the Compose `sqlserver` service with its default parallelism settings (max degree of parallelism 0, cost threshold for parallelism 5): `SearchStatementBoundsTests` 20 passed and 1 failed. A longer one that holds no `[` has each run of `%`, after `*` → `%`, collapsed to one `%`, which matches exactly the same text: with no `ESCAPE` clause every `%` outside a `[...]` set is a wildcard, and a run of them matches what one does. Inside a set a `%` is a member (`[a-%%]%%` and `[a-%]%` match different text), so a pattern holding `[` is never rewritten. A pattern still longer than 4,000 units is matched whole, with no 400 (`src/EpiInfo.Data/Records/SearchSqlBuilder.cs`, "Long patterns"): its condition's long patterns are compiled into one program, bound as one ASCII parameter, which a recursive CTE runs over the column's values in the same single `SELECT`, ended by `OPTION (MAXRECURSION 0)`, so neither the statement text nor its parameter count grows with the pattern, and a condition holding one is never packed. SQL Server matches a literal run of a pattern by the collation's equality, under which one character can rank equal to several (`æ` to `ae`, `ß` to `ss`, `ﬁ` to `fi`) and an ignorable one (`NUL`; the soft hyphen under `Latin1_General_100_CI_AS`; every supplementary character under `SQL_Latin1_General_CP1_CI_AS`) to none, while `_` and a set match exactly one character of the collation and an expansion never straddles a literal and a wildcard (measured: `æ` is `LIKE 'ae'` but not `LIKE 'a_'`, and `xæy` is `LIKE 'x_y'`). So the program reads the pattern as atoms, each a maximal literal run, a `_`, a whole `[...]` set or a run of `%`, and never cuts a literal run between two comparisons. Its steps are windows of whole atoms of at most 3,998 units, compared with `LIKE`; a literal run longer than that, compared with `=`, which has no length limit, with `x` appended to both sides because `=` ignores trailing blanks that `LIKE` keeps; and a set longer than that, cut into pieces. Each step tracks where the text matched so far really ends: a window first tries its own character count, then bisects for the shortest prefix of the rest that `LIKE W + '%'` accepts, which is monotone in the prefix length, extends it to a character boundary of the collation (where the two code units around it are not one `_` and neither is ignorable) and accepts it when it is `LIKE W`; a run step bisects for the first prefix not below the run and accepts the first equal one at a boundary. The segments between runs of `%` are placed in order: the first from the start of the value; each middle one at the leftmost candidate `PATINDEX` finds for its first atoms, retried after a candidate whose steps fail; the last, when it fits a 3,999-unit `LIKE '%' + W`, by that `LIKE`, else, when each of its literal runs fits a window, matched backwards from the end of the value, and otherwise placed as a middle one before an end that only ignorable characters may fill, as a pattern with no `%` ends. ### `=` on two texts: the desktop culture

- **Legacy:** two strings are trimmed and compared with `StringComparer.CurrentCultureIgnoreCase` (`Epi.Core.EnterInterpreter/Rules/Rule_CompareExp.cs:224-227`), so under the desktop's current culture with Windows NLS collation. `NOT` makes the same kind of comparison: it compares its operand's string form, untrimmed, with `"true"` using `StringComparison.CurrentCultureIgnoreCase` (`Epi.Core.EnterInterpreter/Rules/Rule_NotExp.cs:40`).
- **Kept:** the same trimming and a linguistic comparison that ignores case, with the invariant culture, so the answer does not depend on the server; `NOT` compares its operand's text, untrimmed, with `"true"` in that comparison (`src/EpiInfo.CheckCode/Evaluation/Evaluator.cs`, `IsTrueForNot`). The two agree on case, trimming, canonically equivalent forms (a precomposed `é` equals `e` followed by a combining acute accent) and ignorable characters. So `NOT` of `tr` + soft hyphen (U+00AD) + `ue` is false, as in legacy, while `IF` and `AND`, which legacy and the port both test by an ordinal comparison of the lowered form with `"true"` (`Rule_If_Then_Else_End.cs:170`; `Rule_AndExp.cs:41-44`), find that text not true.
- **Why not equal:** the server can run neither the desktop's culture nor NLS. The comparisons differ where NLS treats an expansion as equal, such as `ß` and `ss` (`"straße" = "STRASSE"` holds in legacy and not here), where a desktop culture has its own casing rules, such as the Turkish dotted and dotless `i`, and, for `NOT`'s comparison with `"true"`, wherever NLS and the invariant culture give a character a different collation weight. No seeded program compares such text, and none applies `NOT` to text.

### `=` on numeric text: the desktop culture

- **Legacy:** text against a number is parsed with `double.TryParse(string)` (`Epi.Core.EnterInterpreter/Rules/Rule_CompareExp.cs:123-149, 150-175`), whose styles are `NumberStyles.Float | NumberStyles.AllowThousands`, under the desktop's current culture.
- **Kept:** the same number styles, thousands separators included, with the invariant culture: `,` groups digits and `.` is the decimal point, as en-US reads them, so `"1,000" = 1000` and `"1,000.5" = 1000.5` hold. A result that is not finite is rejected, as .NET Framework rejected an overflow.
- **Why not equal:** the server cannot know the desktop's culture. Under a culture that uses `,` as the decimal separator, such as de-DE, legacy reads `"1,5"` as 1.5 and `"1.000"` as 1000, where the server reads 15 and 1.

### `=` with a boolean on the left that legacy cannot convert

- **Legacy:** with a boolean on the left and a non-empty value of another type on the right, the right side's string form is converted with `ConvertStringToBoolean` (`Epi.Core.EnterInterpreter/Rules/Rule_CompareExp.cs:182-185`; `Epi.Core.EnterInterpreter/EnterRule.cs:64-89`). Only `(+)`, `YES`, `Y`, `TRUE`, `T`, `(-)`, `NO`, `N`, `FALSE` and `F` convert, in any letter case and untrimmed. Any other text, and every number, date or option index, converts to `null`, and the cast of that `null` throws. The exception leaves the whole event block, so its remaining statements do not run; it is logged when errors are suppressed and raised otherwise (`Epi.Core.EnterInterpreter/Rules/Rule_Begin_After_Statement.cs:33-47`; `Rule_Begin_Before_Statement.cs:35-49`; `Rule_Begin_Click_Statement.cs:34-48`).
- **Kept:** the ten spellings convert exactly as in legacy, so `Fever = "No"` holds for an unchecked checkbox and not for a checked one. Every other right side gives one `error` diagnostic, `Type mismatch: a boolean can be compared only with a yes or no value.`, with the statement's line and command. That statement is skipped, the effects of earlier statements stand and the next statement runs, as for `EPIWEEK` without a date.
- **Why not equal:** a field event reports a runtime error as a diagnostic that keeps earlier effects and never blocks a save; it has no counterpart for an exception that ends the block. No seeded program compares a checkbox on the left with anything but `(-)`.

### `=` between a date and text: the desktop culture

- **Legacy:** a date and text are compared by the string forms of both sides, untrimmed, with `StringComparer.CurrentCultureIgnoreCase` (`Epi.Core.EnterInterpreter/Rules/Rule_CompareExp.cs:191-217`). The date's form is `DateTime.ToString()` in the desktop's current culture, such as `1/15/2011 12:00:00 AM` under en-US.
- **Kept:** the string forms of both sides, untrimmed, compared linguistically with the invariant culture, ignoring case. The date's form is `DateTime.ToString()` of the date at 00:00:00 (C-15) in the invariant culture, `01/15/2011 00:00:00`, and the text's form is the text as stored. That form carries a time, as the desktop's form does in every culture, so, as in legacy, a date never equals date-only text: text `"2011-01-15"` does not equal the date 2011-01-15, and neither does `"1/15/2011 12:00:00 AM"`, while `"01/15/2011 00:00:00"` does.
- **Why not equal:** the server does not know the desktop's date format, so it cannot write the date as that culture would, and the invariant culture's form is the same on every server. The ISO wire format `YYYY-MM-DD` (C-15) is not used here, because legacy never compared a date in a date-only form. No seeded program compares a date with text.

### Legal Values options

- **Legacy:** the whole code table is read without `ORDER BY`, the exact-distinct texts of `TextColumnName` are kept with `DataView.ToTable(true, ...)`, which compares values with `Equals`, and a `NULL` row shows as an empty item. With `Sort` = 1 the ComboBox sorts under the process's current culture with `CompareOptions.StringSort`, case-sensitive (`Epi.Core/Services/Fields/TableBasedDropdownField.cs:79-110`; `Epi.Windows.Enter/PresentationLogic/ControlFactory.cs:506, 537-541`).
- **Kept:** the same unsorted rows, every code table of a request read in one batch; the exact-distinct texts as stored, empty and white-space texts included; with `Sort` = 1, one sort by the metadata reader under the API process's current culture with `StringSort`, whose order the form definition keeps (`src/EpiInfo.Data/Metadata/SqlMetadataReader.cs`).
- **Why not equal:** a `NULL` row is not offered, because an option's value and label are both its stored text and a `NULL` has none; leaving the field empty still saves `NULL`, as legacy saves its empty item. Texts the culture ranks equal, such as a decomposed and a precomposed `é`, are ordered ordinally, where legacy's order for them depends on the order of insertion. ### EPIWEEK date text

- **Check code:** any `EPIWEEK` call whose first argument is text, from a Text field or a string literal. No seeded program does this: the one seeded call, `ASSIGN OnsetWeek = EPIWEEK(OnsetDate)` (`FoodHistory` check code line 18, `testdata/sql/03_forms.sql:72`), passes the Date field `OnsetDate`.
- **Legacy behaviour:** `Rule_EPIWEEK` reads any present first argument with `DateTime.TryParse` of its text in the current culture, keeping the time of day, and returns null when that fails, before it reads the first day (`Epi.Core.EnterInterpreter/Rules/Functions/Rule_EPIWEEK.cs:40-47`).
- **Behaviour kept:** text in two families is read with legacy's own lenient parser, `DateTime.TryParse`, in the invariant culture, time of day included:
  - the year-first numeric family: a year of four or more digits, a month and a day separated by `-` or `/`;
  - the named-month family: a day, a full Title-case month name other than `May` (`January` to `April`, `June` to `December`) and a year of four or more digits, as day, month and year (`2 January 2011`), month, day and year (`January 2, 2011`) or year, month and day (`2011 December 31`), with white space between the parts, or a comma and optional white space before a year that comes last, optionally after a full Title-case weekday name (`Sunday` to `Saturday`) and a comma or white space (`Saturday, December 31, 2011`).

  Either may be followed, after `T`, a comma or white space, by `H:mm` with optional `:ss`, an optional `.` or `,` fraction of any length (rounded to ticks, as legacy rounds it) and an optional upper-case `AM` or `PM`, or by an hour with `AM` or `PM`, with surrounding white space allowed. Every spelling of both families holds a year of four or more digits and a day, so no reading takes either from the clock. So `2011-12-31T10:00:00.12345678`, `2011/01/02`, `02011-01-02`, `2011-01-02 10:00 AM`, `2011-05-04 10 PM`, `2011-05-04, 10:00`, `January 2,2011`, `Sunday,January 2,2011 10:00 AM` and `February 28, 2011 13:00` are read as legacy reads them. Text of either shape the parser rejects, such as `2011-02-30`, `2011-01-01T1:05`, a `24:00` time, `February 30, 2011` or a weekday that is not the date's (`Monday, January 2, 2011`, which no culture reads), gives null, as in legacy. The text is read in the Gregorian calendar, as legacy reads it under every culture whose calendar is Gregorian; under a culture with another calendar legacy reads even `2011-01-01` differently, as 1468-01-01 under `th-TH` (Thai Buddhist) and 2632-03-21 under `fa-IR` (Persian). Every other present value, other text included, gives null as a successful call, as legacy does for text it cannot parse. A missing date stays an `error` diagnostic (`src/EpiInfo.CheckCode/Functions/EpiWeekFunction.cs`).
- **Why:** a probe ran `DateTime.TryParse` on 72,092 generated spellings under each of the 892 Gregorian-calendar cultures of .NET 10, the stand-in for the .NET Framework runtime legacy runs on: every one of the 23,624 spellings the port reads as a date was read the same in all 892 cultures and as the port reads it. Outside the families, legacy's result depends on:
  - the culture: a numeric date that is not year-first (`01/02/2011` is 1 February under 711 cultures and 2 January under 181); `.` as the date separator (`2011.01.02` fails under 15 cultures, among them `as`, `en-DK` and `en-FI`); `May`, which `bas`, `bas-CM`, `dua` and `dua-CM` read as another month (`May 5, 2011` is 5 November under `bas` and 5 October under `dua`); abbreviated month and weekday names (`Jan 2, 2011` is 2 June under `st`, `st-LS` and `st-ZA`, and `Sun, January 2, 2011` fails under `to` and `to-TO`); and other casings of the names and a lower-case `am` or `pm`, which `en-US-POSIX` does not read (`january 2, 2011`, `2011-01-02 10:00 pm`);
  - the clock: text without a year takes the current year or date: `1.5` and `1/5` are days of the current year, and `January 2` is 2 January of the current year under 334 cultures and 1 January 2002 under the other 558;
  - the server time zone: a `Z` or offset suffix, as in `2011-01-01T10:00:00+02:00`, is converted to the server's local time.

  No deterministic port can match those readings. The spellings outside the families that legacy reads alike in every culture give null by the bound of the port, not because their reading is unknown: seconds followed by a period and then white space (`2011-01-02 10:00:00.` and a tab; without the white space 105 cultures reject it), white space before a comma (`January 2 , 2011`), a month name run into the year (`2 January2011`), a year and a month without a day, alone or followed after a comma, white space or a dash by more (`2011, 10` and `2011 - 10` read as 1 October 2011, `January 2011 - 10 PM` as 10 January 2011 at noon), and an abbreviated name that collides with no culture's, such as `Tue, 1 February 2011`, because the port reads only full names. Proof: `EpiWeekFunctionTests`.

### A condition with no value

- **Legacy:** an `IF` condition and each operand of `AND` and `NOT` are read through the value's `ToString()` (`Epi.Core.EnterInterpreter/Rules/Rule_If_Then_Else_End.cs:170`; `Rule_AndExp.cs:41-44`; `Rule_NotExp.cs:40`). An empty text, phone-number or GUID field reads as empty text (`Rule_Value.cs:299-332, 400-406`), which is simply not `"true"`. Every other value-less operand is `null`: `(.)`, an empty number, date or Yes/No field, and a function that gives no value. Its `ToString()` throws, so neither branch runs and the exception leaves the whole event block, as for the boolean comparison above.
- **Kept:** the same truth, with the same exemption for an empty text-family field (`text`, `multiline`, `legalValues`), which is not true. Any other value-less operand gives one `error` diagnostic, `A condition has no value.`, with the operand's line and the statement's command. Neither branch of that `IF` runs, the effects of earlier statements stand and the next statement runs.
- **Why not equal:** a field event reports a runtime error as a diagnostic that keeps earlier effects and never blocks a save; it has no counterpart for an exception that ends the block. No seeded program tests a value-less operand: every operand of a seeded `IF`, `AND` or `NOT` is a comparison, which always has a boolean value (`IF Sex = "1"`, `IF NOT FeverTemp = (.) AND Fever = (-)`).

### Find wildcard patterns longer than 4,000 code units

- **Legacy:** the pattern is inlined as an ANSI `varchar` literal (`Epi.Core/Data/Services/CollectedDataProvider.cs:2195-2206`) and runs up to 8,000 single-byte characters; a longer one fails with SQL Server error 8152. Against the `nvarchar` columns the literal is converted to `nvarchar(4000)`, so every character past the 4,000th is dropped without an error and the search answers for the shortened pattern (measured: `a` × 4,000 followed by `b` matches a stored `a` × 4,000).
- **Kept:** every pattern, of any length, on a text, multiline or legal-values field of either form, `CaseReport1.LastName` and the `ntext` `FoodHistory3.BuyLastTenDays` included, is matched whole with the meaning of `col LIKE @p` and every value a parameter ("Wildcard patterns" in "SQL Server limits"): within 4,000 code units as one `LIKE`, past them by the long-pattern program, which compares whole literal runs by the collation's equality and returns the rows one `LIKE` of the whole pattern returns, where the column's collation matches an expansion (`æ` and `ae` under `Latin1_General_100_CI_AS`) or ignores a character (`NUL` and, under the rehearsal database's `SQL_Latin1_General_CP1_CI_AS`, every supplementary character; measured: `N'abc' LIKE N'%😀%'` and `N'a😀b' LIKE N'ab'` are both true there) included. A grid `q` past the limit runs as the same program's literal contains ("Grid q"). One case is a 400: a pattern holding a `[...]` set longer than 4,000 code units that has no closing `]`, or that cannot be cut into sets of at most 3,998 code units, each cut between two members where neither is `-` or a zero-width joiner, the second is neither `^` nor a combining mark and the two are not one surrogate pair, is a 400 under the field's canonical name, `<field> search patterns cannot hold a [...] set longer than 4000 characters that has no closing ] or that cannot be cut into sets of at most 3998 characters that keep its members and negation.`, after the form's metadata is read and before any Find statement is sent. And a literal run longer than a `PATINDEX` pattern, in a Find pattern or a long `q`, is sought by the leftmost hit of 33 of its prefixes, so a match is found while no character of the column's collation ranks equal to more than 33 text elements of the run: measured on SQL Server 2022, of the 11,557 BMP characters whose compatibility decomposition has three or more code units, the 314 that `Latin1_General_100_CI_AS` and the 71 that `SQL_Latin1_General_CP1_CI_AS` rank equal to it span at most three text elements (`ﬃ` for `ffi`), and `ﷺ` (U+FDFA) equals its 18-character decomposition under neither.
- **Why not equal:** SQL Server's `LIKE`, `PATINDEX`, `CHARINDEX` and `REPLACE` all refuse an `nvarchar` pattern past 4,000 code units (error 8152), so no single comparison takes a longer one, and converting it to a `varchar` pattern in the database code page, as legacy's literal was, is inexact: it replaces every character outside the code page, and on a double-byte code page an 8,000-byte `varchar` holds fewer than 8,000 characters, so SQL Server shortens the pattern without an error (measured: 5,000 `あ` cast under `Japanese_CI_AS` to `varchar(8000)` keep 4,000). The target therefore matches the whole pattern in steps, and does not reproduce legacy's shortening, which answered for a pattern other than the one written. A set matches one character, and SQL Server reads its `^`, its `-` and a combining mark by their neighbours in the whole set (`[a-c-e]` matches `a`, `b`, `c` and `e` but neither `-` nor `d` under `Latin1_General_100_CI_AS`, and also `-` under `Latin1_General_100_BIN2`), so a set longer than any pattern SQL Server takes is evaluated only as pieces that keep those readings. An unclosed one has no collation-independent meaning (`[a` matches `a` under `Latin1_General_100_CI_AS` and nothing under `Latin1_General_100_BIN2`), and one with no such cut, such as a chain of ranges, has no pieces, so neither runs and both are the one 400. A prefix of a literal run can end inside a value character the collation expands, which then defeats it, and no number of prefixes covers a character expanding into more text elements than that number, so the seek's 33 prefixes bound it, far past the three measured. No seeded value needs a pattern longer than 4,000 units.

### Repeated field names

- **Legacy:** `GetFields` reads a view's `metaFields` rows ordered by `ControlTopPositionPercentage`, then `ControlLeftPositionPercentage`, and adds each row's field to the view unless the view already contains a field of that name; such a row is logged as already existing, "This field has not been imported.", and left out (`Epi.Core/Data/Services/MetadataDbProvider.cs:1141-1161, 1229-1234, 1366-1386`). `Contains` compares `Name.ToLowerInvariant()`, so letter case is ignored (`Epi.Core/Collections/NamedObjectCollection.cs:154-167`). - **Legacy:** opening a form computes the permissions of the connected principal once (`Epi.Windows.Enter/Forms/EnterMainForm.cs:1429-1452`, `CheckAndSetPermissions` at `:1458-1464`), which the SQL Server driver reads with `HAS_PERMS_BY_NAME` per table (`Epi.Data.SqlServer/SqlDatabase.cs:1804-1810`). - **Kept:** the same flags, `HAS_PERMS_BY_NAME(<table>, 'OBJECT', 'INSERT')` and `'UPDATE'` for the base and every page table, read for the connected principal on the tables the catalogue confirms, so a table it does not hold gets no entry and is denied (`src/EpiInfo.Data/Permissions/SqlPermissionReader.cs`). They are read afresh on every write and never cached. A `POST` without `canInsert`, a `PUT` without `canUpdate` and a `DELETE` without `canDelete` return 403 with nothing written (`src/EpiInfo.Api/Services/RecordService.cs`, `IsAllowed`). A `PUT` is checked again inside its update transaction, after the locked read and the required gate and before any statement that changes data: the repository reads the permissions of the base table and every page table on that transaction's connection, and refuses the update with 403, nothing written, when UPDATE is denied on any of them or INSERT on the table of a page whose row is missing, so a grant revoked while the update waited on the lock is a refusal, not a failed statement (`src/EpiInfo.Data/Records/SqlRecordRepository.cs`, `MayApplyUpdateAsync`; `SqlPermissionReader.ReadResolvedAsync`). An insert on a form whose page table, or its record key column, the catalogue lacks is refused before any statement is sent, so no record is committed without one of its page rows ("Insert on a form whose page table is missing" in "Design reconciliations"). The client disables New, Save and Delete by the same flags (`web/src/components/FormView.tsx`, `web/src/components/RecordNavigator.tsx`), and refuses a save started by leaving a record the same way as an explicit one: with `canInsert` `false` for a new record, or `canUpdate` `false` for a stored one, the editor sends no request and shows the permission banner, keeping the draft and offering Discard edits (`web/src/state/useRecordEditor.ts`, `runSave`). Page UPDATE is checked always, where legacy checks it only when insert is allowed ("Permission rule" in "Design reconciliations").
- **Why not equal:** the rule is ported, but a denial cannot be proved against the real database. A denied principal needs a new login or user, which the unchanged-database rule excludes, and the seeded login holds every permission on both forms, so on the rehearsal database every flag is granted and no write is denied. Denials are proved only through the fake store. This stays unresolved.

### Sign-only number entry

- **Fields:** every Number field a user can type into: `CaseReport` `Age` and `AntibioticUseDays`, and `FoodHistory` `CaseID`, `Age`, `Latitude`, `Longitude` and `FeverTemp`. The read-only `OnsetWeek` takes no entry.
- **Legacy:** every Number field is a `MaskedTextBox`, because `NumberField` is `IPatternable` (`Epi.Core/Services/Fields/NumberField.cs:13`; `Epi.Windows.Enter/PresentationLogic/ControlFactory.cs:379-385`). On leaving it, `control_Leave` counts the digits and the characters equal to the current culture's negative sign or decimal separator, and clears the box when it holds such a character and no digit, such as `-`, `.` or `-.` (`Epi.Windows.Enter/Forms/Canvas.control.events.cs:538-559`).
- **Kept:** the text as typed. `NumberInput`'s `interpret` turns blank text into `null` and text that reads as a finite number into that number, kept exact as a `bigint` or a decimal where a double would round it, and keeps any other text, sign-only text included, as the raw string (`web/src/components/fields/NumberInput.tsx:28-35`; `web/src/api/client.ts`, `numberFromText`, which gives no number for `-`, `.` or `-.`); its `onBlur` only raises the field event and leaves the text alone (`NumberInput.tsx:101-108`). Client validation reports the string as not a number, "Enter a number." (`web/src/validation/clientValidation.ts:55, 205-210`, `checkType`), and the save stops on that error before any request (`web/src/state/useRecordEditor.ts:1091-1095`). The server answers such text from any caller with a 400, "A finite number is expected." (`src/EpiInfo.Domain/Validation/RecordValidator.cs:547-579`, `TryCoerce`, the message at `:574`; `src/EpiInfo.Domain/Validation/ValidationMessages.cs:62`).
- **Why not equal:** the client plan does not port the clearing on leave. `NumberInput` keeps sign-only or separator-only text such as `-`, `.` or `-.` as typed (`NumberInput.tsx:54-59`), so the user completes or clears it where legacy cleared it. A partial entry that holds a digit is not part of this gap: `37.` keeps its typed display while its value is the number 37, which can be saved, and legacy, which clears only text with no digit, keeps it too. This stays unresolved. No stored value is affected, because such text is rejected and never written.
- **Proof:** no test pins it. `RecordValidatorTests` (`ValidateInput_NumberGivenNonNumber_IsNumberExpected`) pins the server's answer for other text on a number field (`abc`, `98`), not for sign-only text.

### Fixed-width text columns (nchar)

- **Fields:** none seeded. Every seeded character column is `nvarchar(n)` or `ntext` ("Column families" in "Field types found"), so the gap is reached only by a text, multiline or legal-values field whose page column is `nchar(n)`.
- **Legacy:** the text is written as given, as a parameter, and only empty text becomes `NULL` (`Epi.Core/Data/Services/CollectedDataProvider.cs:1293-1320`), so SQL Server stores shorter text padded with spaces to n; the record load takes the stored value as it is, padding included (`dataRow[...]`, `:1737`). Two entries that differ only in trailing spaces therefore store one value, and a short legal choice comes back as a padded text.
- **Kept:** the legacy behaviour. Writes: text of up to n UTF-16 code units is admitted on `nchar(n)`, as on `nvarchar(n)`, and longer text is a field-level 400, `The value is longer than the <n> characters this field can store.`, with nothing written (`src/EpiInfo.Domain/Metadata/FieldTypeMapper.cs`, `IsRepresentable`; `src/EpiInfo.Domain/Validation/RecordValidator.cs`). Admitted text, a logon-name stamp on an `nchar(n)` stamp column included, is bound as given, and SQL Server pads shorter text with spaces to n (`src/EpiInfo.Data/Sql/ColumnValueConverter.cs`, `ToParameter` and `ToSystemParameter`). Reads: an `nchar(n)` value is returned as stored, padding included, and never trimmed (`ColumnValueConverter.FromDbValue`), so API values equal direct SQL. Options are the code-table texts verbatim, padded when the code table is `nchar` (`src/EpiInfo.Data/Metadata/SqlMetadataReader.cs`, `ToOptions`), and a legal value must equal one of them ordinally (`RecordValidator`).
- **Why not equal:** on fixed-width storage a write and read of short text cannot round-trip exactly, because SQL Server stores it padded. Trimming on read would return values other than the stored ones, which reads must not do (`DATA-01`, SC-4), and refusing short text would break the plan's admission of up to n code units on `nchar(n)`. Two inputs that differ only in trailing spaces therefore store one value, and a saved short legal choice reads back as a padded text that is no option: resubmitting that read-back value verbatim is a 400, `The value is not one of the field's legal values.`, while choosing the option again is accepted. These stay unresolved, as in legacy.
- **Proof:** the tests named under "Fixed-width text (`nchar(n)`)" in "Column families", among them these `ReservedWordIdentifierTests` on session `#` tables: `FixedWidthColumns_ShortValues_AreStoredPaddedAndReadBackAsStored`, where a short legal choice and short text written through the repository's insert are stored padded at `DATALENGTH` 10 on `nchar(5)`, direct SQL and the repository's read return the padded texts, and the validator accepts the short choice again and refuses the padded one as not a legal value; `FixedWidthColumns_TextsDifferingOnlyInTrailingSpaces_StoreOneValue`, where `ab` and `ab ` store one value; `FixedWidthColumns_FullWidthChoiceEndingInSpaces_RoundTripsExactly`, where a full-width value ending in spaces round-trips exactly; `FixedWidthColumns_ShortValueWrittenByDirectSql_ReadsBackAsStoredPaddingIncluded`, where a short value written by direct SQL reads back padded; and `FixedWidthStampColumns_ShortLogonName_IsStoredPaddedByInsertUpdateAndSoftDelete`, where, on a base table whose logon-name stamps are `nchar(255)`, an insert, an update and a soft delete with a short logon name succeed and store it padded at `DATALENGTH` 510. Results in "Changed after the run".
